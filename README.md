# Мини-бэкенд IPTV/OTT на Go

REST-сервис: отдаёт абоненту список каналов и ссылку на live-поток, хранит пользователей, каналы и подписки в SQLite, доступ — по HTTP Basic Auth. Плюс три усложнения из задания: подписки (бессрочные и ограниченные по времени), админ-панель и кэширование под высокую нагрузку.

Обязательная часть сделана первой и полностью; усложнения — так, чтобы они не ломали обязательную часть: каждый слой можно выключить, не переписывая остальные.

* Стек: **Go 1.26, только стандартная библиотека** и один внешний пакет — драйвер SQLite ([обоснование](#зависимости)).
* Никаких фреймворков, DI, ORM и генераторов: роутинг — `net/http.ServeMux` с паттернами методов, SQL — руками, шаблонов нет.
* ~4 500 строк кода и ~2 600 строк тестов. Читается за вечер: сначала `cmd/iptv/main.go`, дальше по слоям.

## Быстрый старт

### Вариант 1 — docker compose

```bash
docker compose up --build          # http://localhost:8080, панель http://localhost:8080/admin/
```

Схема создаётся и наполняется демо-данными при первом запуске, база лежит в named-волюме `iptv-data`. Остановить: `Ctrl-C` или `docker compose down` (с удалением базы — `down -v`).

### Вариант 2 — go run

```bash
go run ./cmd/iptv                  # :8080, база в ./data/iptv.db (каталог создаётся сам)
```

Проверить себя:

```bash
go build ./... && go vet ./... && go test ./...
```

### Если Go не установлен локально

В репозитории есть [`hack/go.sh`](hack/go.sh) — он выполняет те же команды в контейнере `golang:1.26` и пишет кэши только в `.devcache/` внутри проекта:

```bash
./hack/go.sh build ./...
./hack/go.sh test ./...
CGO_ENABLED=1 ./hack/go.sh test -race ./...   # детектору гонок нужен cgo
./hack/go.sh run ./cmd/iptv                   # публикует :8080
```

### Проверка целиком, не читая код

```bash
./hack/smoke.sh          # 44 проверки HTTP-поведения против запущенного сервиса
./hack/shutdown-check.sh # SIGTERM: корректный drain, код выхода 0, без паники
```

## Тестовые учётные данные

Вставляются сидом **только в пустую базу** — перезапуск не затирает изменённые пароли и не дублирует каналы ([seed.go](internal/seed/seed.go)).

| Логин     | Пароль         | Роль          | Каналы                                                          |
| --------- | -------------- | ------------- | --------------------------------------------------------------- |
| `admin`   | `admin12345`   | администратор | все активные (роль ≠ подписка)                                   |
| `viewer`  | `viewer12345`  | абонент       | 1, 2, 3 — бессрочно; 4 (НТВ) — до +7 дней; 5 — нет подписки      |
| `viewer2` | `viewer12345`  | абонент       | 1 — бессрочно; 2 — подписка уже истекла                          |
| `blocked` | `blocked12345` | абонент       | выключен, демонстрирует 401                                      |

Каналов шесть: «Первый», «Россия 1», «Матч ТВ», «НТВ», «ТНТ», «Ретро ТВ». Последний **выключен** — для демонстрации 404 на существующем канале.

> Это демо-данные. В проде нужен TLS перед сервисом (Basic Auth без HTTPS — это передача пароля в открытом виде) и другие пароли.

## Примеры запросов

Список каналов, которые абоненту доступны:

```bash
curl -s -u viewer:viewer12345 http://localhost:8080/api/v1/channels
```

```json
{"channels":[{"id":1,"number":1,"name":"Первый","available":true,"expires_at":null},
 {"id":2,"number":2,"name":"Россия 1","available":true,"expires_at":null},
 {"id":3,"number":3,"name":"Матч ТВ","available":true,"expires_at":null},
 {"id":4,"number":4,"name":"НТВ","available":true,"expires_at":"2026-10-20T14:22:08Z"}],
 "count":4,"mode":"available"}
```

Все активные каналы с признаком доступности (например, чтобы показать «Подключите ТНТ»):

```bash
curl -s -u viewer:viewer12345 'http://localhost:8080/api/v1/channels?all=true'
```

Ссылка на просмотр:

```bash
curl -s -u viewer:viewer12345 http://localhost:8080/api/v1/channels/1/playback
```

```json
{"channel_id":1,"number":1,"name":"Первый",
 "url":"http://stream.example.com/live/ch01/index.m3u8?exp=1791907484&sig=19a99e6852ae9725be5d3e40038a4ff4adb2a04150ca840270df7fe3dec9e3ef",
 "expires_at":"2026-10-13T16:04:44Z"}
```

Ссылка подписана HMAC-SHA256 от пары «путь канала + момент истечения», живёт 15 минут (`-stream-ttl`) и перегорает сама. `stream.Signer.Verify` — ровно та проверка, которую делает edge-сервер; она покрыта тестами, включая «подпись одного канала не подходит к другому».

Краевые случаи:

```bash
curl -s -u viewer:viewer12345 http://localhost:8080/api/v1/channels/5/playback   # 403 нет подписки
curl -s -u viewer:viewer12345 http://localhost:8080/api/v1/channels/6/playback   # 404 канал выключен
curl -s -u viewer:viewer12345 http://localhost:8080/api/v1/channels/99999/playback # 404 канала нет
curl -s -u viewer:viewer12345 http://localhost:8080/api/v1/channels/abc/playback # 400 некорректный id
curl -s -u viewer:неверный http://localhost:8080/api/v1/channels                 # 401 + WWW-Authenticate
curl -s -o /dev/null -D - -u viewer:viewer12345 http://localhost:8080/api/v1/channels # ETag → повторный запрос с If-None-Match даст 304
```

Админ-часть (только для `is_admin`):

```bash
ADMIN=http://localhost:8080/api/v1/admin
curl -s -u admin:admin12345 $ADMIN/users                     # список, хэш пароля не отдаётся никогда
curl -s -u admin:admin12345 $ADMIN/channels
curl -s -u admin:admin12345 $ADMIN/users/2/subscriptions
curl -s -u admin:admin12345 -H 'Content-Type: application/json' \
     -X PUT -d '{"expires_at":"2027-01-01T00:00:00Z"}' $ADMIN/users/2/subscriptions/5   # выдать/продлить
curl -s -u admin:admin12345 -X DELETE $ADMIN/users/2/subscriptions/5                    # отозвать, 204
curl -s -u admin:admin12345 -H 'Content-Type: application/json' \
     -X POST -d '{"number":10,"name":"Культура","stream_path":"/live/ch10/index.m3u8"}' $ADMIN/channels  # 201
curl -s -u admin:admin12345 -H 'Content-Type: application/json' \
     -X PATCH -d '{"is_active":false}' $ADMIN/channels/7                                 # выключить
curl -s -u admin:admin12345 $ADMIN/cache                 # что делает кэш: попадания, промахи, merge, stale
```

Панель администратора — `http://localhost:8080/admin/` (те же учётные данные, браузер сам покажет форму).

Диагностика: `GET /healthz` (процесс жив), `GET /readyz` (база доступна; для healthcheck'а контейнера).

## API

| Метод и путь                                     | Доступ  | Назначение                                     |
| ------------------------------------------------ | ------- | ---------------------------------------------- |
| `GET /api/v1/channels`                           | пользователь | Список каналов. `?all=true` — все активные с флагом доступности |
| `GET /api/v1/channels/{id}/playback`             | пользователь | Ссылка на поток                                 |
| `GET /api/v1/admin/users`                        | админ   | Все пользователи                               |
| `POST /api/v1/admin/users`                       | админ   | Создать (`is_active` по умолчанию true)         |
| `GET/PATCH /api/v1/admin/users/{id}`              | админ   | Читать / менять (логин, пароль, флаги)          |
| `GET /api/v1/admin/channels`                     | админ   | Все каналы, включая выключенные                 |
| `POST /api/v1/admin/channels`                    | админ   | Создать канал                                   |
| `PATCH /api/v1/admin/channels/{id}`              | админ   | Менять номер, название, путь, вкл/выкл          |
| `GET /api/v1/admin/users/{id}/subscriptions`     | админ   | Подписки пользователя                           |
| `PUT /api/v1/admin/users/{id}/subscriptions/{channelId}` | админ | Выдать/заменить (`{"expires_at": null \| RFC3339}`) |
| `DELETE /api/v1/admin/users/{id}/subscriptions/{channelId}` | админ | Отозвать, `204`                          |
| `GET /api/v1/admin/cache`                        | админ   | Счётчики кэшей                                  |
| `GET /admin/`                                    | админ   | HTML-панель                                     |
| `GET /healthz`, `GET /readyz`                     | все     | Пробки                                          |

Коды ответов:

| Код | Когда |
| --- | ----- |
| `200` | успех; `304` — если `If-None-Match` совпал с ETag списка каналов |
| `201` | создано (POST в админке) |
| `204` | отзыв подписки |
| `400` | некорректный id, некорректный `?all`, невалидное тело или поля |
| `401` | нет учётных данных, неверный пароль, неизвестный логин, выключенный пользователь (всегда с `WWW-Authenticate`) |
| `403` | аутентифицирован, но нельзя: не-админ в админке, нет подписки на канал |
| `404` | нет канала/пользователя/подписки, канал выключен, неизвестный маршрут |
| `405` | путь есть, метода нет (это делает `ServeMux`); `307` — нормализация пути, например при `//` в URL |
| `406`/`415` | тело не `application/json` в админ-записи |
| `409` | конфликт: занятый логин или номер канала, попытка отключить самого себя |
| `429` | слишком много неудачных входов, есть `Retry-After` |
| `500`/`503` | внутренняя ошибка / недоступна база. Подробности — только в логе |

Единый формат ошибки, включая 404 на неизвестном маршруте:

```json
{"error":{"code":"subscription_required","message":"this channel requires an active subscription","request_id":"231d44b339d55e0e"}}
```

`code` стабиленный и машинный, `message` — для человека, `request_id` совпадает с заголовком `X-Request-Id` и со строкой лога. Внутренностей (текст SQL, пути, стек) в ответе не бывает — это отдельный тест.

Конфигурация — флаги и одноимённые переменные окружения `IPTV_*` (флаг сильнее переменной, переменная сильнее значения по умолчанию):

```bash
./hack/go.sh run ./cmd/iptv -h        # полный список; основные:
# -addr                 :8080                 адрес слушателя
# -db                   ./data/iptv.db        путь к файлу SQLite (или :memory:)
# -seed                 true                  наполнять пустую базу демо-данными
# -pbkdf2-iterations    150000                стоимость хэширования паролей
# -stream-base-url      http://stream.example.com  откуда начинается ссылка на поток
# -stream-key           (генерируется)         HMAC-ключ ссылок; при пустом — временный на процесс + WARN
# -stream-ttl           15m                    время жизни ссылки
# -cache-ttl            5m                     потолок жизни записи кэша
# -cache-version-ttl    1s                     как часто перечитывается счётчик версий данных
# -auth-cache-ttl       5s                     сколько помнится проверенная пара логин/пароль
# -login-limit          10                     неудачных входов с одного адреса за окно
# -request-timeout      5s                     бюджет обработки одного запроса
# -log-level/-log-format info / json
```

## Усложнения

### 1. Подписки

**Модель.** Отдельная таблица грантов `subscriptions(user_id, channel_id, expires_at)` с `UNIQUE (user_id, channel_id)`. Пакеты каналов сознательно не делал: это следующая таблица поверх той же модели (`package_id` вместо `channel_id`), и решение о том, какие пакеты существуют и как тарифицируются, принимает бизнес, а не схема. Нужное сейчас поведение — «бессрочно» и «до момента» — закрывается одной таблицей без раскатки.

`expires_at IS NULL` — бессрочно, значение в прошлом — уже истекла. **Никакого крона и никаких фоновых задач**: доступ вычисляется на каждом чтении сравнением `expires_at` с текущим временем, поэтому подписка перестаёт работать сама, в любую секунду, без чьего-либо участия. Это же видно в тестах: у `viewer2` грант с истёкшей датой, и доступ к каналу отказывается без каких-либо записей.

**Что возвращает список.** По умолчанию — только доступные каналы (как в примере из задания). Плюс `?all=true`: все активные каналы, у каждого `available` и `expires_at`. Оба режима собираются одним и тем же SQL (`LEFT JOIN` каналов с грантами этого пользователя) и оба кэшируются; клиенту не нужно гадать. Выключенные каналы не видны ни в одном режиме — их нет и в выдаче, и в статистике `count`.

**Код ответа без подписки — `403` с `subscription_required`,** а не 404:

* канал для абонента существует и показан в витрине (`?all=true`, «Подключите ТНТ»), и 404 противоречил бы собственному списку;
* 401/404 не дают клиенту различить «нет денег» и «сломалось», а это принципиально разные состояния для приставки;
* сокрытие тут не аргумент: id каналов известны из витрины, а наличие/отсутствие подписки — про самого абонента, новых секретов 403 не раскрывает.

Канал, которого нет, и выключенный канал — `404`, как и просили. Различаются кодами (`channel_not_found` / `channel_disabled`), чтобы по логу было понятно, что произошло.

**Роль ≠ подписка.** Администратор видит все активные каналы без грантов: им нужно смотреть и проверять вещание. При этом выключенный канал недоступен и ему.

### 2. Админ-панель

Сделаны обе половины: **admin API** (`/api/v1/admin/*`, JSON) и **HTML-панель** (`/admin/`), которая является тонким клиентом этого API, а не второй реализацией правил. Так «что может администратор» живёт в одном месте — в `internal/service/admin.go`, и панель с curl не могут разойтись.

Страница, CSS и JS вшиты в бинарник (`embed`), инлайн-скриптов нет — поэтому CSP остаётся строгой: `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; …`. Панель работает на `fetch` с `credentials: 'same-origin'` и использует те же Basic-учётные данные, что и загрузка страницы.

Функции: просмотр и создание каналов и пользователей, вкл/выкл, смена пароля, выдача/продление/отзыв подписок, счётчики кэша. Удалений пользователей и каналов нет — вместо удаления выключение: удалённый клиент оставил бы висящие гранты, а экстренное отключение важнее.

Безопасность панели:

* все маршруты — под Basic Auth **и** проверкой роли; просмотрщик получает 403 и на API, и на страницу;
* записи требуют `Content-Type: application/json`, а при наличии `Origin` он обязан совпасть с хостом запроса. Межсайтовая форма не может поставить ни то, ни другое, поэтому сохранённые браузером Basic-учётные данные нельзя использовать с чужой страницы;
* значения в DOM пишутся через `textContent`, разметка в названии канала не превращается в скрипт;
* администратор не может отключить сам себя и снять с себя права — 409 `self_lockout`, иначе один неверный клик оставляет систему без входа (сделать это может другой администратор);
* пароли в логи и в ответы не попадают: `password_hash` помечен `json:"-"`, в логах есть факт «password_changed», но не значение.

### 3. Кэширование под высокую нагрузку

Задача: «после сбоя миллион приставок одновременно перезапрашивает список каналов». Ответ в трёх частях.

**Инвалидация по версии данных, а не по TTL.** В таблице `data_version` лежат монотонные счётчики групп данных: `users` и `catalog`. Любая запись в админке увеличивает нужный счётчик **в той же транзакции**, что и сама запись, — значит, невозможно увидеть новые данные со старой версией. Запись в кэше хранит версию, из которой она построена: счётчик не сдвинулся — запись всё ещё правильная, сколько бы она ни лежала.

Побочный, но важный эффект: **инвалидация работает между экземплярами без обмена сообщениями**. Экземпляр A сделал запись и поднял счётчик; экземпляр B заметит это в течение `-cache-version-ttl` (по умолчанию 1 с) и перестроит свои записи. Никакого Redis, pub/sub или кластера не нужно.

Чтение счётчика — единственный запрос к базе на горячем пути, и он сам кэшируется на 1 с (`internal/cache.Versions`) и схлопывается для параллельных запросов. То есть при любой интенсивности трафика база видит **не больше двух SELECT в секунду на экземпляр** (по одному на группу данных), а не по одному на запрос.

**TTL остаётся, но для того, что не является записью.** Подписка истекает по времени — никто при этом ничего не пишет и счётчик не двигает. Поэтому загрузчик возвращает время жизни записи, и для списка каналов это `min(cache-ttl, ближайший момент истечения гранта)`, для решения о доступе к каналу — то же самое. Запись не может пережить факт, из которого она построена; крутить «проверку истечения» по таймеру не нужно.

**Шквал одинаковых запросов схлопывается.** Параллельные промахи по одному ключу ждут одну загрузку (single-flight на `sync.WaitGroup`), а не идут в базу стадом: из миллиона запросов после сбоя к базе придёт один запрос на ключ на экземпляр. Остальные получат результат или дождутся.

**Если база упала — отдаём устаревшее.** Запись живёт ещё `-cache-stale-ttl` (по умолчанию 10 минут) и при ошибке перезагрузки отдаётся, а не превращается в шторм 503. Исключение — «определённые» отказы, помеченные `cache.Permanent`: отрицательное решение по подписке или выключенный пользователь из устаревшей записи никогда не обслуживаются. Для кэша учётных данных окно устаревания урезано до 30 секунд — это максимум, на который отключённый аккаунт мог бы попасть внутрь при неудачном стечении обстоятельств.

**Что кэшируется конкретно.**

| Кэш | Ключ | Значение | TTL по умолчанию | Инвалидация |
| --- | ---- | -------- | ---------------- | ----------- |
| Список каналов | пользователь + режим + флаг админа | уже готовые JSON-байты + ETag | 5 мин или до ближайшего истечения | версия `catalog` |
| Доступ к каналу | пользователь + канал | канал и решение (в том числе отрицательное) | 5 мин или до истечения гранта | версия `catalog` |
| Учётные данные | логин + HMAC от пароля | id, логин, роль | 5 с | версия `users` |
| Версии данных | имя группы | число | 1 с | — |

Список каналов кэшируется **замаршаленным**: собирают его один раз на пользователя на TTL, а не на запрос. Побочный приятный эффект — стабильные байты дают осмысленный `ETag`, и приставка, опрашивающая список периодически, получает `304` без тела.

Размер кэша ограничен LRU (`-cache-max-entries`, по умолчанию 8192 на кэш), чтобы список ключей не рос вместе с числом абонентов.

**Как кэш обновляется после админ-панели.** Экземпляр, который сделал запись, чистит свои кэши немедленно (`InvalidateAll`) — следующий запрос уже увидит новое состояние; остальные экземпляры подтянут изменения в пределах секунды через счётчик. Для кэша учётных данных это важно: отключение аккаунта или смена пароля на «своём» экземпляре работают сразу, на чужих — за ≤1 с. Окно задокументировано здесь и в коде; гарантировать нулевое окно между экземплярами можно только общей шиной инвалидации (в «что бы я улучшил»).

Отрицательные решения кэшируются намеренно: «нет подписки» может изменить только запись, а запись всегда двигает счётчик. Это то, что спасает при атаке на закрытые каналы, — и ровно то место, где я нашёл настоящий баг (см. [тесты](#тесты)): потерянный in-flight-слот превращал такое кэшированное «нет» в вечное.

## Ключевые решения

Подробности — по ссылкам; это список «что выбрано и почему», «что выбрано и почему», чтобы не искать по всему документу.

| Решение | Обоснование | Где объяснено |
| ------- | ----------- | ------------- |
| SQLite + драйвер на чистом Go, одна внешняя зависимость | запуск одной командой, статический бинарник без cgo, тесты без окружения | [Зависимости](#зависимости) |
| Пароли — PBKDF2-HMAC-SHA256 из stdlib, самодокументируемый формат | нет внешней зависимости для KDF, стоимость поднимается без миграции | [Безопасность](#безопасность) |
| Basic Auth поверх TLS | требуется заданием; просто, stateless, проверяется curl; TLS — снаружи | [Безопасность](#безопасность) |
| Отметки времени — unix-секунды | у SQLite нет типа даты; сравнения не зависят от таймзоны и формата; API отдаёт RFC 3339 | [Допущения](#допущения) |
| Истечение подписки — сравнением на чтении, без крона | невозможно «проспать» окончание; нет фоновых задач и рассинхрона | [Усложнения](#усложнения) |
| Инвалидация кэша по счётчику версий в базе, а не по TTL | работает между экземплярами без брокера; запись и версия живут в одной транзакции | [Усложнения](#усложнения) |
| Без подписки — 403, канал не существует/выключен — 404 | канал виден абоненту в витрине; 401/404 не различают «нет денег» и «сломалось» | [Усложнения](#усложнения) |
| Ссылка на поток — HMAC с коротким сроком, а не «вечный» путь | украденная ссылка перегорает; проверка — та же функция, что покрыта тестами | [Примеры запросов](#примеры-запросов) |
| Выключенный канал недоступен и администратору | «выключен» означает «не вещает», а не «скрыт от одного пользователя» | [Усложнения](#усложнения) |
| Удалений нет, только отключение | гранты и история не повисают; экстренное отключение важнее | [Допущения](#допущения) |
| Панель — тонкий клиент admin API | правила доступа живут в одном месте, панель и curl не разойдутся | [Усложнения](#усложнения) |
| Ограничитель перебора в памяти процесса | не нужен Redis для одной ноды; при N экземплярах разрешение растёт — место для него балансировщик | [Безопасность](#безопасность) |
| Никакого DI/фреймворка/ORM | 14 пакетов читаются без карты; зависимость строго вниз, подмена не нужна | [Структура](#структура) |

## Нагрузка

Замерено бенчмарками (`./hack/go.sh test -run '^$' -bench . ./internal/api/`) на i7-12700H, 20 ядер. Замеряется весь стек через реальный TCP: роутинг, middleware, Basic Auth, сервис, кэш, JSON. Тестовый клиент и сервер делят одну машину, поэтому цифры — нижняя оценка, а не «нагрузочное тестирование».

| Сценарий | время/запрос | ~rps | SQL-запросов на запрос |
| -------- | ------------ | ---- | ---------------------- |
| `GET /api/v1/channels`, кэш прогрет, 20 параллельных клиентов | 4,3 мкс | ~230 000 | ~0 (плюс 1 SELECT в секунду на счётчик версий) |
| `GET /api/v1/channels/{id}/playback`, параллельно | 5,4 мкс | ~185 000 | ~0 + один HMAC на запрос |
| Тот же список без кэша (пустой кэш на каждой итерации) | 11,2 мкс | ~89 000 | 1 запрос каталога |
| Один последовательный клиент (упор в round-trip) | ~45 мкс | — | — |
| Первая запись после инвалидации (холодная сборка) | 158 мкс | — | 2 |

Что это значит для «миллиона приставок»: узкое место — не CPU и не JSON, а число запросов к базе. Кэш меняет его с «один на запрос» на «две строки в секунду на экземпляр (счётчики версий) плюс одна сборка списка на пользователя за TTL», а single-flight не даёт этим сборкам стартовать массово. Дальше масштабирование — это несколько экземпляров за балансировщиком (кэш и инвалидация между ними уже работают), TLS на терминаторе и `private, must-revalidate, max-age=30` для списка каналов — 30 секунд устаревания покрывают задержку инвалидации между экземплярами.

SQLite при этом остаётся одно-писательным: чтения в WAL не мешают записи, но несколько экземпляров на одном хосте — это уже тонкое место, и честный ответ на «масштаб в несколько машин» — переход на PostgreSQL (код к этому готов: `store` — это интерфейс из четырёх небольших файлов, SQL в нём стандартный).

## Безопасность

* **Пароли** не хранятся в открытом виде и не восстанавливаются: PBKDF2-HMAC-SHA256, 150 000 итераций, случайная соль 128 бит, 256-битный ключ. Замерено `BenchmarkKDFCost`: одна проверка ≈ **18 мс** на i7-12700H, то есть перебор стоит ~55 попыток в секунду на ядро. Формат хэша самодокументируемый — `pbkdf2-sha256$итерации$соль$ключ`, поэтому `-pbkdf2-iterations` поднимается без миграции: старый хэш продолжает работать, а при удачном входе молча пересоздаётся с текущей стоимостью.
* **Задержка проверки.** Проверка неизвестного логина тратит столько же CPU, сколько проверка известного (`hasher.Burn`), сравнение ключей — `subtle.ConstantTimeCompare`. Различить «нет такого логина» и «неверный пароль» по времени и по ответу нельзя: 401 один и тот же.
* **Перебор.** Неудачный вход стоит токена из «ведра» на IP (`-login-limit`, по умолчанию 10 в минуту), после исчерпания — `429` с `Retry-After`, и до дорогой проверки пароля дело не доходит. Успешные запросы токен не тратят. Ограничитель локальный в процессе: при N экземплярах разрешение формально умножается на N, честное место для него — балансировщик; в README это отмечено как компромисс.
* **SQL-инъекций нет по построению**: все запросы параметризованы, динамической конкатенации значений нет; отдельный тест создаёт пользователя с логином `x' OR 1=1; DROP TABLE users;--` и проверяет, что это данные, а таблица на месте. Отдельно проверяется, что `PRAGMA user_version = N` собирается из числа, полученного из имени миграции.
* **Секреты не утекают.** В ответы — никогда (ошибки рендерятся из фиксированного списка кодов, паника даёт 500 без деталей). В лог — тоже: тестируется напрямую, что в вывод не попадают ни пароли, ни заголовок `Authorization`, ни `password_hash`. HMAC-ключ ссылок не логируется; если он не задан, генерируется случайный на процесс и об этом пишется `WARN`.
* **HTTP-гигиена**: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, строгий CSP с default-deny (см. [панель](#2-админ-панель)), `Cache-Control: no-store` там, где ответ может содержать учётные данные (401, админ-эндпоинты), и `private, must-revalidate` для персональных, но кэшируемых (список каналов, playback), лимит тела запроса 64 КиБ (`http.MaxBytesReader`), таймауты сервера (заголовок 5 с, чтение 15 с, запись 20 с, idle 90 с) плюс бюджет запроса 5 с через `context.WithTimeout`, так что медленный клиент не держит соединение и соединение с базой.
* **Полномочия**: проверка роли идёт после аутентификации на каждом админ-маршруте; `password_hash` не покидает слой хранения; сид не трогает непустую базу, чтобы перезапуск не «вернул» известные демо-пароли.

## Тесты

```bash
go test ./...                                    # 76 тестов и 54 подтеста
CGO_ENABLED=1 go test -race -count=2 ./...       # без гонок
```

Тесты проверяют поведение, а не детали реализации, и не требуют внешнего окружения: SQLite создаётся во временном каталоге каждого теста, сеть — `httptest`, время — инъекционные часы (`internal/testutil.Clock`), стоимость хэширования понижается через `-pbkdf2-iterations`.

| Пакет | Что проверяется |
| ----- | --------------- |
| `internal/cache` | попадание/промах, инвалидация по версии, single-flight, TTL и TTL загрузчика, обслуживание устаревшего, `Permanent`, LRU-лимит, параллельная работа под `-race` |
| `internal/store` | решения о доступе для всех комбинаций (бессрочно/с окончанием/истекло/нет гранта/выключен/неизвестен/админ), истечение без записи, счётчики версий, upsert и отзыв, конфликт уникальности, «вредные» строки как данные, повторное открытие |
| `internal/api` | реальный HTTP-стек целиком: коды и формат ошибок, аутентификация и роли, подпись ссылки и её проверка, `ETag`/`304`, `HEAD`, применение записи админки к следующему же запросу, изменение от «другого экземпляра» через счётчик версий, истечение подписки без записи, rate limit, 415/CSRF, панель, отсутствие секретов в ответах и в логах, поведение при смерти базы |
| `internal/password` | формат хэша, соль, проверка, «нужно повысить стоимость», мусор вместо хэша, длины паролей |
| `internal/stream` | форма ссылки, проверка подписи, отказ при подмене пути/подписи/срока, режим без подписи, отказ пустого ключа |
| `internal/limit` | успехи не тратят бюджет, неудачи блокируют, восстановление, изоляция клиентов, чистка |
| `internal/config` | приоритет флагов над окружением, валидация, внятная ошибка на плохой `IPTV_LOG_LEVEL` |
| `internal/seed` | минимальный набор из задания, идемпотентность, что документированные пароли — действительно те, что в базе |

Ещё две проверки, которые трудно выразить юнит-тестом:

* [`hack/smoke.sh`](hack/smoke.sh) — 44 HTTP-проверки против запущенного сервиса (коды, заголовки, формат ошибок, применение записи админки, подписанные ссылки);
* [`hack/shutdown-check.sh`](hack/shutdown-check.sh) — старт контейнера, SIGTERM: код выхода 0 (не 143/137), логируется `shutting down` → `stopped`, то есть слушатель и база закрыты до выхода, без паник.

**Тесты нашли три реальных бага**, и все три оставлены в истории коммитов как есть:

1. in-flight-слот кэша не удалялся после загрузки — первое решение по ключу (в том числе «нет подписки») становилось вечным; виден только на последовательности «запись → тот же запрос»;
2. «бессрочная» подписка и «нет подписки» были неразличимы по `expires_at IS NULL` — список каналов молча пустел для правильных данных; помогло добавление `grant_id` в выборку;
3. стоимость аутентификации тратилась на успешные входы тоже — легитимный клиент мог «исчерпать» собственный лимит и получить 429.

Чего в тестах сознательно нет: нагрузочного тестирования (для этого нужен отдельный стенд и настоящая база), UI-тестов панели (её проверяют smoke-проверки API и ручной прогон в браузере), тестов реального потокового сервера (его нет по условию).

## Структура

```
cmd/iptv/main.go        сборка мира: конфиг → база → кэш → сервисы → HTTP; graceful shutdown
internal/config         флаги + IPTV_* окружение + валидация
internal/store          SQL, миграции (embed, PRAGMA user_version); доступ описан запросом, не знает про HTTP
internal/store/migrations  0001_init.sql
internal/service        бизнес-правила: что видно, что стоит денег, что может админ; валидация; ошибки API
internal/api            маршруты, middleware, обработчики, admin API
internal/auth           Basic Auth → принципал, кэш учётных данных, CSRF/Origin-проверка
internal/cache          кэш с инвалидацией по версии данных, single-flight, stale-окно, LRU
internal/httpx          единый конверт ошибки, JSON, id запроса
internal/password       PBKDF2, самодокументируемый формат, повышение стоимости
internal/stream         сборка и проверка подписанной ссылки на HLS
internal/limit          token bucket для неудачных входов
internal/panel          HTML/CSS/JS админки (embed), тонкий клиент admin API
internal/seed           демо-данные в пустую базу
internal/testutil       инъекционные часы для тестов
hack/                   go.sh (Go в Docker), smoke.sh, shutdown-check.sh
Dockerfile, docker-compose.yml, Makefile
```

Порядок зависимостей строго однонаправленный: `cmd → api → {auth, service} → {store, cache, stream, password, limit}`. Слоёв три — транспорт (`api`, `panel`, `auth`), домен (`service`, `cache`, `stream`, `password`, `limit`) и хранение (`store`). Из `store` ничего верхнего не импортируется, из `service` — только хранилище и кэш; HTTP не протекает вниз (кроме стабильных ошибок в `httpx`, которые как раз и определены как «то, что видит клиент»), SQL не протекает наверх. Каждый слой читается отдельно.

## Зависимости

Прямая зависимость одна:

```
modernc.org/sqlite v1.60.1
```

Почему она, а не `mattn/go-sqlite3`: это **чистый Go без cgo** (порт SQLite через transpile), поэтому `CGO_ENABLED=0` даёт статический бинарник, который запускается в минимальном контейнере, а `go test` работает на любой машине без тулчейна C. `database/sql` требует драйвер — это тот случай, когда стандартная библиотека прямо оставляет выбор за разработчиком.

Почему SQLite как база: задание разрешает любую, а требование «запуск одной командой» лучше всего удовлетворяет встроенная БД — ни сервора, ни миграций окружения. Взяты осознанные настройки: WAL (читатели не ждут писателя), `busy_timeout=5000` (писатель ждёт, а не падает с «database is locked»), `foreign_keys=1` (иначе каскады в схеме не работают), `synchronous=NORMAL`, пул из 16 соединений.

Всё остальное — стандартная библиотека, включая то, что часто тянут пакетом:

* роутинг и сервер — `net/http` (паттерны с методами с Go 1.22);
* хэширование паролей — `crypto/pbkdf2` (argon2/bcrypt пришлось бы приносить);
* HMAC подписи ссылок — `crypto/hmac` + `crypto/sha256` + `crypto/subtle`;
* миграции — `embed` + `PRAGMA user_version`;
* логи — `log/slog` (JSON по умолчанию), `slog.NewLogLogger` подхватывает внутренний лог `net/http`;
* single-flight — ~40 строк в `internal/cache` вместо `golang.org/x/sync`;
* шаблоны не нужны: панель — статические файлы, а не шаблонизация.

## Что бы я улучшил

По убыванию пользы при данном объёме:

1. **argon2id вместо PBKDF2.** жёсткий по памяти KDF — текущий стандарт для паролей; формат хэша уже версионирован, так что замена — один файл и `NeedsUpgrade`-миграция без остановки сервиса. Придержка — требование стандартной библиотеки из задания.
2. **PostgreSQL как целевая база.** SQLite честен для «одна команда» и для одного хоста, но несколько экземпляров на разных машинах требуют серверной базы: тот же `store` переведётся на `pgx`/`lib/pq` с минимальными правками (SQL стандартный, метаданные-счётчики те же), добавятся `READ ONLY` реплики для каталога каналов.
3. **Метрики и трейсинг.** Сейчас есть `/api/v1/admin/cache` со счётчиками и структурированные логи с `request_id`. Для продакшена просится `/metrics` (частота попаданий, длительности, очередь single-flight, `served_stale`) и OpenTelemetry-трейссы: «почему этот запрос пошёл в базу» должно быть видно в trace, а не в логах.
4. **Инвалидация между экземплярами в ноль.** Сейчас ≤1 с на чужом экземпляре — осознанный компромисс вместо общей шины. Если этого мало: Redis pub/sub или `LISTEN/NOTIFY` в Postgres на те же счётчики версий; интерфейс `VersionSource` для этого уже есть.
5. **Аутентификация для реальных клиентов.** Basic Auth удобен и в задании, но для приставок лучше короткоживущие токены: тогда список каналов можно кэшировать на CDN (`Cache-Control: public` вместо `private`), а подписанные ссылки это уже закрывают. Плюс нормальная ротация учётных данных и отзыва сессий.
6. **Аудит изменений.** Админ-действия сейчас видны только в логе. Таблица `audit_log (кто, что, когда, до/после)` — это то, о чём спрашивает бухгалтерия и безопасники.
7. **`readiness` во время shutdown.** На время дрейнования отдавать 503 из `/readyz`, чтобы балансировщик раньше времени не слал запросы уходящему экземпляру.
8. **CI**: `go build/vet/test -race`, `golangci-lint`, сборка образа, `docker compose up` + `hack/smoke.sh` как приёмочный тест, проверка `govulncheck`.
9. **Мелочи, до których не дошли руки**: пагинация и фильтрация в списке каналов (при тысячах каналов ответ станет большим), `Idempotency-Key` для админ-записей, `Accept-Language` для сообщений,  `?all=true` c фильтрами по пакетам.

| Вопрос | Решение | Почему |
| ------ | ------- | ------ |
| Что такое «ссылка на просмотр» | HLS-плейлист с подписанным `exp`/`sig` | реального стрим-сервера нет, поэтому интереснее сделать ссылку корректной и защищённой от подмены |
| Хранение отметок времени | unix-секунды в INTEGER | у SQLite нет типа даты; сравнения точные и без зависимости от таймзоны и формата, API отдаёт RFC 3339 |
| Формат id | числовой, из URL-пути | как в примере задания; некорректный id — 400, а не «нет такого канала» |
| Список каналов по умолчанию | только доступные | совпадает с примером; расширенный режим — отдельным параметром |
| Ответ без подписки | 403 `subscription_required` | см. [усложнение 1](#усложнения) |
| Выключенный канал | 404 | просили «несуществующий или выключенный → 404»; внутри коды разные |
| Админ и подписки | роль даёт доступ ко всем активным каналам | оператору нужно смотреть вещание; гранты при этом не выдумываются |
| Удаление пользователей/каналов | не сделано, только выключение | иначе гранты и история висят; экстренное отключение важнее |
| TLS | снаружи (терминатор/балансировщик) | типичная схема; без HTTPS Basic Auth бесполезен — в README это написано крупно |
| IP клиента | `RemoteAddr`, `X-Forwarded-For` не доверяем | иначе лимит неудачных входов обходится подделкой заголовка; за прокси адрес надо брать из доверенного заголовка — это настройка развёртывания |
| Один экземпляр или много | много, с общими счётчиками версий в базе | кэш и инвалидация не требуют обмена между процессами; узкое место — SQLite, см. выше |
| Миграции | embed + `PRAGMA user_version` | «схема создаётся автоматически при старте» и одновременно честный путь для правок |
| Полный список настроек | `-h` (`./hack/go.sh run ./cmd/iptv -h`) | здесь перечислены основные; каждая продублирована переменной `IPTV_*` |
| Стоимость пароля в тестах | понижается флагом | тесты идут секунды, а не минуты; формат и поток при этом те же |
