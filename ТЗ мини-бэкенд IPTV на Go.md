# **ТЗ: мини-бэкенд IPTV на Go**

## **О задании**

Нужно написать на Go небольшой бэкенд IPTV/OTT-сервиса: REST API, которое отдаёт абоненту список ТВ-каналов и ссылку на просмотр live-потока. Задание приближено к реальной задаче нашей команды, но сильно упрощено.

Обязательная часть небольшая и рассчитана на несколько часов. Дальше есть усложнения: какие из них делать и делать ли вообще, решаете вы. Нам важнее увидеть, как вы думаете и принимаете решения, чем количество реализованных функций.

* **Срок:** 7 календарных дней с момента получения задания.  
* **Ориентир по трудозатратам:** 4–6 часов на обязательную часть, ещё 4–12 часов, если берётесь за усложнения.  
* **Вопросы** по заданию можно задавать в любой момент. Если что-то не описано, примите разумное решение сами и зафиксируйте его в README.  
    
  После сдачи мы проведём ревью и обсудим решение с вами на техническом интервью (около часа).

## **Обязательная часть**

Сервис хранит пользователей и каналы в базе данных и отдаёт по REST API два ресурса: список каналов и ссылку на просмотр канала. Доступ к API только для аутентифицированных пользователей.

### **Данные**

Минимальный набор, расширять можно:

| Сущность | Что хранить |
| :---- | :---- |
| Пользователь | логин, пароль (в каком виде хранить, решаете вы), признак «активен» |
| Канал | название, номер или позиция в списке, ссылка на поток или данные для её построения, признак «активен» |

База данных любая: SQLite, PostgreSQL или другая на ваш выбор. Схема создаётся автоматически при старте или миграцией. При первом запуске должны появиться тестовые данные: хотя бы 2 пользователя и 5 каналов.

### **Аутентификация**

HTTP Basic Auth. Если пользователь существует, активен и пароль верный, запрос выполняется. Иначе сервис отвечает 401 Unauthorized с заголовком WWW-Authenticate.

### **API**

| Метод и путь | Назначение |
| :---- | :---- |
| GET /api/v1/channels | список каналов, доступных для просмотра |
| GET /api/v1/channels/{id}/playback | ссылка на live-поток канала |

Пример ответа списка каналов:

{  
  "channels": \[  
    {"id": 1, "number": 1, "name": "Первый"},  
    {"id": 2, "number": 2, "name": "Россия 1"}  
  \]  
}  
Пример ответа со ссылкой:

{  
  "channel\_id": 1,  
  "url": "http\://stream.example.com/live/ch1/index.m3u8"  
}  
Формат JSON и пути даны как ориентир. Их можно менять и расширять, если вы объясните решение в README. Реального потокового сервера нет: достаточно отдать корректно сформированную ссылку на HLS-плейлист.

Ожидаемое поведение в краевых случаях:

* несуществующий или выключенный канал → 404;  
* некорректный id → 400;  
* ошибки отдаются в JSON единого формата, без внутренних подробностей вроде текста SQL-ошибки.

## **Усложнения (по желанию)**

Усложнения необязательны, их можно делать в любом порядке и любом объёме. Лучше одно усложнение, сделанное аккуратно, чем три наспех. Отметьте в README, что реализовано.

### **1\. Подписки**

Пользователь видит и смотрит не все каналы, а только те, на которые у него есть подписка. Подписки бывают двух видов:

* **бессрочные**, которые администратор включает и выключает вручную;  
* **ограниченные по времени**, которые действуют до заданного момента и после него перестают давать доступ без чьего-либо участия.

Модель данных выбираете сами: подписка на отдельный канал, на пакет каналов или что-то иное. Также решите и опишите, что возвращает список каналов (только доступные или все с признаком доступности) и какой код ответа получает пользователь, запросивший ссылку на канал без подписки.

### **2\. Админ-панель**

Простой интерфейс для управления пользователями, каналами и подписками (если они реализованы): просмотр, создание, изменение, включение и выключение. Доступ только для администраторов.

Форма на ваше усмотрение: HTML-страницы, отдаваемые самим сервисом, или отдельный admin API. Дизайн не оцениваем, оцениваем работоспособность и безопасность.

### **3\. Кэширование под высокую нагрузку**

Представьте, что на API приходят десятки тысяч запросов в секунду: например, после сбоя миллион приставок одновременно перезапрашивает список каналов. Сделайте так, чтобы сервис выдерживал такой поток и не перегружал базу данных.

Опишите в README, что и где кэшируется, как и когда кэш обновляется после изменений через админ-панель, и какие компромиссы вы приняли.

## **Технические требования**

* **Язык:** Go 1.26 или новее.  
* **Стандартная библиотека по максимуму.** HTTP-сервер, роутинг, JSON, логирование, конфигурация, шаблоны и тесты пишутся на stdlib. Сторонние зависимости допустимы там, где stdlib не справляется: драйвер БД, при необходимости хэширование паролей и т. п. Каждую зависимость кратко обоснуйте в README.  
* **Простота.** Не нужны фреймворки, DI-контейнеры, ORM, генераторы кода и микросервисная обвязка. Решение должно легко читаться за один вечер.  
* **Структура на ваше усмотрение.** Деление на пакеты, слои и файлы не регламентируем: нам интересно, как вы организуете код сами.  
* **Конфигурация** через переменные окружения или флаги: адрес, путь или DSN базы данных и т. п.  
* **Корректная остановка.** По SIGTERM сервис завершает текущие запросы и закрывает ресурсы.  
* **Логи** структурированные, без паролей и других секретов.

Качество обязательной части весит больше, чем число усложнений. Решение без усложнений, но чистое и продуманное, может получить оценку выше, чем «всё сразу», сделанное небрежно.

| Критерий | На что смотрим |
| :---- | :---- |
| Работоспособность | запускается по README, API ведёт себя как описано, корректно обрабатывает краевые случаи |
| HTTP и REST | коды ответов, заголовки, формат ошибок, таймауты сервера |
| Код | читаемость, обработка ошибок, работа с context, отсутствие гонок |
| Структура | понятное деление на части, отсутствие лишних абстракций |
